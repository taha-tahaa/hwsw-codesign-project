================================================================================
1. OVERVIEW
================================================================================

WHAT THE BENCHMARK DOES
-----------------------
pyflate is Paul Sladen's stand-alone pure-Python DEFLATE (gzip) and bzip2
decoder.  pyperformance drives it over data/interpreter.tar.bz2 - 67,562
compressed bytes that expand to 399,360 bytes - and checks the result against a
built-in MD5 (afa004a630fe072901b1d9628b960974).  That checksum is the
correctness oracle used throughout this project.

The workload is bzip2 only (magic 0x425a).  The gzip path is never exercised.

LIBRARIES USED
--------------
Almost none, and that is the point.  The benchmark deliberately implements
decompression in Python rather than calling libbz2, so it measures the
interpreter executing bit-manipulation and table-lookup code.  Imports are
hashlib (checksum), struct (int2byte), os, and pyperf (timing).

ALGORITHM AND DATA STRUCTURES
-----------------------------
A bzip2 block is decoded in four stages, in this order:

  1. Huffman decode      variable-length prefix codes -> symbol indices
  2. Move-to-front (MTF) symbol indices -> byte values, with the alphabet
                         reordered after each hit
  3. Inverse BWT         un-permute the block via a pointer chain
  4. RLE                 expand runs of >= 4 identical bytes

Baseline data structures:

  BitfieldBase / Bitfield / RBitfield
      Bit cursor over a file object.  RBitfield is MSB-first and is the one
      bzip2 uses.  Reads accumulate one BYTE at a time via f.read(1).

  HuffmanLength / HuffmanTable / OrderedHuffmanTable
      A Python list of HuffmanLength objects sorted by (bits, code).
      populate_huffman_symbols() assigns canonical MSB-first codes.

  favourites
      The MTF alphabet: a list of 1-byte bytes objects, reordered per symbol.

  bwt_transform / bwt_reverse
      T[] is a Python list of ints; the block is rebuilt by chasing
      end = T[end] and appending L[end] to a list.

2. INITIAL ANALYSIS
================================================================================

METHODOLOGY
-----------
Three views were combined, as in lecture 4, because no single tool answers both
"where" and "why":

  perf record + flame graph   WHERE the machine spends cycles, per Python
                              function (CPython 3.12's -X perf trampoline)
  cProfile                    call counts, which perf does not give
  perf stat counters          WHY: IPC, cache misses, branch misses

A tooling note that changed the method.  The project brief suggests

    perf record -F 999 -g -- python3-dbg -m pyperformance run --bench ...

and two things go wrong with it:

  (a) pyperformance/pyperf build a virtualenv and re-exec the benchmark in a
      CHILD process using that interpreter - which is not python3-dbg unless
      --python is passed.  perf then samples process machinery, not the decoder.
      tools/profile_target.py runs the workload in-process instead, so every
      sample belongs to the code under study.

  (b) Getting Python FUNCTION NAMES out of perf needs CPython's perf
      trampoline, which is `-X perf` and exists only in 3.12+.  naranja7 runs
      3.12.3, so it works here and the flame graphs carry py:: frames.  The
      course QEMU guest (Ubuntu 22.04) ships CPython 3.10, where it does NOT
      exist and perf will only show _PyEval_EvalFrameDefault.  That is why the
      scripts detect the version and always emit cProfile as a fallback.

  One practical trap worth recording: the trampoline writes /tmp/perf-<pid>.map
  and `perf script` needs that file to resolve py:: frames.  Anything that
  clears /tmp between record and script silently loses every Python name - the
  graph still renders, it just becomes interpreter soup.  Record and collapse
  in one pass.

WHAT THE PROFILE ACTUALLY SAYS
------------------------------
The headline is NOT "Huffman decoding is slow".  Three findings drove the work:

  1. The linear scan is not the problem.  find_next_symbol walks a
     (bits, code)-sorted table, which invites "the scan is too deep".  But
     148,271 calls to it produced only 341,601 snoopbits calls - a ratio of
     2.3, not ~250.  Move-to-front keeps the hot symbols at short code lengths,
     so the scan almost always exits after two probes.
     => The cost is not scan depth.  It is that decoding ONE symbol costs about
        seven Python function calls: find_next_symbol, ~2.3 snoopbits, a
        readbits, and several _mask.
     => The fix must remove CALLS, not iterations.  This is the single most
        important observation in the analysis, and it is the opposite of what
        the benchmark's own comment ("room for improvement in the Huffman
        bit-matcher") suggests at first reading.

  2. move_to_front is far more expensive than call-count profiling suggests.
     cProfile ranks it around 8%; perf puts it at 19.28% - second overall.
     cProfile charges per CALL, so it over-weights functions that make many
     calls and under-weights a function that is simply slow inside.
     move_to_front rebuilds a list from three slices and two concatenations on
     every one of its 92,803 invocations, and the real machine feels that far
     more than a call-count profiler does.  This is exactly why the lecture
     insists on sampling profilers rather than instrumentation alone.

  3. _mask is called 655,017 times to compute (1 << n) - 1, an expression that
     depends only on n, which takes about 20 distinct values.  And the stream
     is consumed one BYTE at a time through _read -> f.read(1): 67,562
     Python-level buffered reads.

  4. The inverse BWT is a textbook irregular access pattern: end = T[end] is a
     dependent load with no spatial locality, un-prefetchable, exactly the case
     the memory-hierarchy lecture calls out.  bwt_transform additionally built
     its histogram with sorted(L) plus 256 bytes.find() scans of the block.

FLAME GRAPHS
------------

================================================================================
3. OPTIMIZATIONS
================================================================================

All optimizations preserve byte-identical output.  tools/verify.py decodes with
both implementations and compares the full 399,360-byte result plus its MD5;
script_pyflate.sh runs it as a gate before any timing is taken.

O1 - CANONICAL HUFFMAN DECODE (replaces the linear table scan)
--------------------------------------------------------------
populate_huffman_symbols() already assigns CANONICAL MSB-first codes, so the
table has algebraic structure the scan ignores.  build_decode_tables()
precomputes the standard limit/base/perm arrays once per Huffman table, after
which a symbol is decoded by:

    zvec = next min_len bits
    while zvec > limit[zn]: zn += 1; zvec = (zvec << 1) | next_bit
    sym  = perm[zvec - base[zn]]

O(codelen - min_len) cheap integer steps, no per-candidate object access, and -
crucially - no function calls.

O2 - INLINED BIT READER
-----------------------
The whole input is read once into a bytes object, and the bit cursor
(bitbuf, bitcnt, pos) is held in LOCAL VARIABLES inside decode_huffman_block.
Decoding a symbol now performs zero Python function calls.  The _Reader class
still exists for the cold path (headers, table setup) and hands its state to
and from the hot loop, so there is one implementation of the bit arithmetic.
The mask table is precomputed once rather than recomputed 655,017 times.

O1 and O2 are inseparable in measurement: the canonical decoder is what makes
inlining possible, and the inlining is what turns the algorithmic win into a
wall-clock win.

O3 - INVERSE BWT
----------------
Histogram computed directly with a 256-bin count plus a prefix sum, replacing
sorted(L) and 256 bytes.find() scans.  Reconstruction writes into a
preallocated bytearray by index instead of appending to a list.

O4 - MOVE-TO-FRONT
------------------
list.pop(i) + list.insert(0, v) performs the same reordering as a single
C-level memmove, replacing three slices and two concatenations.  The alphabet
is kept as ints rather than 1-byte bytes objects, removing an allocation per
emitted symbol.  Given finding 2 above, this matters considerably more than the
call-count profile implied.

O5 - OUTPUT ASSEMBLY
--------------------
Symbols accumulate into a bytearray instead of a list of ~767,000 one-byte
bytes objects joined at the end, and the final RLE pass indexes the block
directly rather than slicing per byte.

DELIBERATELY NOT DONE
---------------------
  * No C extension, no numpy, no ctypes.  The benchmark exists to measure the
    interpreter; replacing it with libbz2 would score a huge "speedup" while
    measuring nothing and teaching nothing.
  * The gzip path is untouched and falls back to the baseline decoder, so no
    previously working input stops working - the "don't break the user's code"
    rule from the accelerator lecture, applied to software.
  * Randomised bzip2 blocks remain unsupported, exactly as in the baseline.

APPROACHES CONSIDERED AND REJECTED
----------------------------------
  * A full 2^20-entry lookup table per Huffman group would decode in one step,
    but bzip2 allows up to 6 tables of code length <= 20; that is ~6M entries
    to BUILD per block, for a block that decodes ~148k symbols.  Table
    construction would cost more than it saves.  A two-level LUT (fast 10-bit
    table + canonical fallback) is the sound middle ground and is the natural
    next step - it is also what the hardware does.
  * numpy for the inverse BWT: an added dependency for a stage the ablation
    shows is worth only ~2%.

THIS TABLE IS THE PROOF OF THE THESIS
-------------------------------------
Look at IPC: 2.73 -> 2.85.  Essentially unchanged.  The optimized code is NOT
using the CPU more efficiently per instruction - it is executing 2.31x FEWER
INSTRUCTIONS, and the runtime improved by 2.38x.  Those two numbers matching is
the hardware-level confirmation that the speedup came from deleting interpreter
work (function calls, frame setup, argument tuples, temporary objects), exactly
as the call-count analysis predicted.  Nothing here was won by being clever
with the microarchitecture.

The secondary effects follow from the same cause: 10.4x fewer cache misses
because ~767,000 one-byte objects are no longer allocated and chased, and 5.4x
fewer branch mispredictions because the per-candidate comparison loop in
find_next_symbol - a data-dependent branch the predictor cannot learn - is gone
entirely.

PER-OPTIMIZATION ATTRIBUTION (tools/ablate.py, best of 7, naranja7)
--------------------------------------------------------------------
Ablation reverts ONE optimization at a time from the fully optimized build and
measures the slowdown.  Marginal costs do not sum to the total - the
optimizations interact - so this is a ranking, not a decomposition.

    variant                             best (ms)    marginal cost
    ---------------------------------   ---------    -------------
    baseline (all optimizations off)        724.2
    fully optimized                         306.7
      without O3 (inverse BWT)              311.4    +4.6 ms (+2%)

    Reverting the inverse BWT costs only 2%.  Since the total saving is ~418 ms
    and O3 accounts for ~5 ms of it, O1+O2 - the canonical decoder and the
    inlined bit reader - together with O4 and O5 are responsible for
    essentially all of the speedup.

    Honest caveat: O1 and O2 cannot be ablated independently, because the
    inlined loop has no call boundary to monkey-patch.  Their combined effect
    is what is being attributed.

A DISTINCTION WORTH MAKING CAREFULLY
------------------------------------
In the OPTIMIZED build, bwt_reverse is 35.81% of runtime - the second largest
item in the profile.  Yet ablating O3 changes the total by only 2%.  These are
not in conflict, and confusing them is an easy way to misread a profile:

    share of time   how much of the remaining runtime a stage occupies
    ablation cost   how much that stage's OPTIMIZATION bought

The inverse BWT is expensive in both builds; O3 made it somewhat cheaper but
could not change its fundamental character, because a pointer chase through a
400 KB array is latency-bound and no amount of Python restructuring fixes that.
That is precisely why it is the stage the hardware accelerator targets with
on-chip SRAM - see section 5.

================================================================================
5. HARDWARE ACCELERATION PROPOSAL
================================================================================

TARGET AND DESIGN PATTERN
-------------------------
Target: the bzip2 back end - Huffman decode, MTF, inverse BWT.

This is a DATAFLOW design, not a systolic array, and the reason is structural.
Huffman codes are variable length: the number of bits consumed per symbol is
data-dependent (1..20).  A systolic array has no control circuitry and consumes
one input per cycle unconditionally - "garbage in, garbage out" if an input is
not ready.  A variable-rate bit stream would immediately mis-align it.  Every
interface in this design therefore carries valid/ready handshakes, and the bit
window retires a data-dependent width each cycle.

(The raytrace accelerator in report_raytrace.txt is the systolic counterpart.
The two benchmarks were chosen so that one motivates each of the two dominant
accelerator paradigms from the lecture.)

INTERFACES: INPUTS AND OUTPUTS
------------------------------
  Clock / reset          clk, rst_n.  Target 800 MHz in a 16 nm-class process;
                         the critical path is window mux -> 20 comparators ->
                         priority encoder -> subtract -> perm SRAM read.

  Compressed in          AXI4 read, 32-bit data + valid/ready + last.
                         Peak demand 1 word / 32 cycles at 20 bits/symbol;
                         the interface is never the bottleneck.

  Decompressed out       AXI4 write, 8-bit data + valid.  Widened to 64 bit in
                         a real build by packing 8 bytes before the write port.

  CSR                    AXI4-Lite, map in bzip2_accel_top.v:
                           0x00 CTRL (START/ABORT)     0x18 ORIG_PTR
                           0x04 STATUS (BUSY/DONE/     0x1C BLOCK_LEN
                                ERR/UNSUPPORTED)       0x20 MIN_LEN
                           0x08 SRC_ADDR  0x0C SRC_LEN 0x24 TBL_CTRL
                           0x10 DST_ADDR  0x14 DST_LEN 0x28 TBL_LIMIT
                                                       0x2C TBL_BASE
                                                       0x30 PERM_CTRL
  Interrupt              irq, asserted on DONE.

  Internal widths        window 20 b (max bzip2 code length)
                         symbol  9 b (alphabet <= 258)
                         limit/base 22 b signed
                         BWT index 20 b (900 KB max block)

  On-chip memory         perm    258 x 9 b        ~0.3 KB
                         MTF     256 x 8 b        ~0.25 KB
                         T[]     900k x 20 b      ~2.25 MB  <-- dominates area
                         L[]     900k x 8 b       ~0.9 MB

INTERNAL ARCHITECTURE
---------------------
huffman_decoder.v is the heart.  Instead of iterating over code lengths, it
evaluates ALL of them at once:

    for L in 1..20 (in parallel hardware):
        code_L = window[19 -: L]                 // top L bits
        hit_L  = lvalid[L] && L >= min_len && code_L <= limit[L]
    sel = lowest L with hit_L                    // priority encoder
    sym = perm[code_sel - base[sel]]

Because Huffman codes are prefix-free, the shortest accepting length is the
unique correct one - so the priority encoder is exact and needs no backtracking.
The software's serial while-loop becomes 20 parallel 22-bit magnitude
comparators plus a 20-input priority encoder: ONE CYCLE, independent of code
length.

mtf_unit.v turns the list reorder into a single-cycle shift-enable across a
256-entry register file: every entry at index <= hit shifts down one slot
simultaneously.  Given that MTF measured 19.28% of baseline runtime - second
overall - this block earns its area.

bwt_reverse_engine.v keeps T[] and L[] in on-chip SRAM.  The chain is
inherently serial - cur <- T[cur] - so the win is not parallelism but LATENCY:
a guaranteed 1-cycle SRAM access replaces a dependent DRAM load that no
prefetcher can predict.  This is the stage that is still 35.81% of the
OPTIMIZED software runtime, so it is the right thing to put in hardware.

ACCELERATION JUSTIFICATION AND EXPECTED SPEEDUP
-----------------------------------------------
Why this component: the Huffman + MTF stages are 56.7% of baseline runtime
(37.4% + 19.3%), and the inverse BWT is still 35.8% of the OPTIMIZED runtime.
Between them they are almost the whole program, and all three are small,
well-defined, stream-shaped kernels with stable interfaces.

Estimate, stated with its assumptions:

    Symbols in the benchmark block          148,271
    Accelerator: 1 symbol/cycle @ 800 MHz   ~185 us for Huffman+MTF
    BWT chase: 399,360 cycles @ 800 MHz     ~499 us
    Total on-chip                           ~0.7 ms

    Optimized software (naranja7)           309 ms
    Baseline software (naranja7)            733 ms

Assumptions, which matter more than the number: the block already resides in
on-chip SRAM (T[]/L[] fit), DMA setup and IOMMU mapping are excluded, and the
host is not otherwise stalled.  Real end-to-end gain would be far lower than
the raw ratio suggests, because for a 67 KB input the PCIe round trip and
driver overhead would dominate - which is exactly why an accelerator like this
belongs on-die or on a SmartNIC next to the data, not behind a discrete PCIe
card.  Stating that honestly is more useful than quoting a 400x figure.

HW/SW INTERFACE
---------------
The three rules from the accelerator-design lecture, applied concretely:

  Rule 1 - do not expect users to change their code.
      Python code still calls bz2.decompress().  Nothing above the library moves.

  Rule 2 - if software must change, confine it to the runtime/library.
      Only the decompressor library gains a fast path: map the source and
      destination buffers, push the Huffman tables through the CSR window,
      write CTRL.START, sleep on the interrupt.

  Rule 3 - do not break the user's code.
      START returns UNSUPPORTED for a randomised block or one larger than the
      on-chip index SRAM, and the driver silently falls back to software.
      Reduced benefit beats a broken program.  The optimized Python module
      mirrors this: a gzip input falls back to the baseline decoder.

Security: the accelerator is a DMA master behind the IOMMU, with per-device page
tables, so it can only touch buffers the driver mapped for this request.  This
is the same protection boundary discussed for NICs, and the reason the driver
maps per-request instead of pinning memory permanently.

PERFORMANCE / AREA / POWER TRADE-OFFS
-------------------------------------
  Area is dominated by memory, not logic.  T[] + L[] for a 900 KB block is
  ~3.15 MB of SRAM; the decoder logic (20 comparators, a priority encoder, a
  256-entry register file) is negligible beside it.

  The obvious trade: shrink the on-chip block memory and spill T[] to DRAM.
  That reintroduces exactly the dependent-load latency the accelerator existed
  to remove, so the inverse BWT would collapse back toward software speed while
  Huffman decode stayed fast.  Supporting only the smaller bzip2 block sizes
  (-1 .. -4, i.e. 100-400 KB) is the better compromise, with larger blocks
  reported as UNSUPPORTED and handled in software under Rule 3.

  Frequency: the critical path is the comparator-plus-priority-encoder chain.
  Splitting it into two pipeline stages would push past 1 GHz at the cost of a
  one-cycle bubble on table switches (every 50 symbols in bzip2), which is
  nearly free - a good trade if timing closure demands it.

  Power: the MTF register file's parallel 256-entry shift is the largest
  per-symbol switching cost.  Gating the shift for index 0 (a no-op, and common
  because MTF concentrates hits at the front) removes a large fraction of that
  toggling for a trivial comparator.


================================================================================
6. CONCLUSION
================================================================================

The optimized decoder is 2.38x faster than the baseline on naranja7 while
producing byte-identical output, verified by MD5 over all 399,360 decompressed
bytes.

The lesson is not "use a better Huffman algorithm".  The profile showed the
linear table scan almost always exits after about two probes, so the scan was
never really the problem - the problem was that decoding one symbol cost
roughly seven Python function calls.  Removing calls, not iterations, produced
the 5.5x reduction in call count and with it the speedup.  The hardware
counters settle the argument: IPC barely moved (2.73 -> 2.85) while
instructions retired fell 2.31x against a 2.38x runtime improvement.  The
machine did not get smarter; it was simply asked to do far less.

Two methodology points proved their worth.  First, cProfile and perf disagreed
about move_to_front - 8% versus 19.28% - and perf was right, because
instrumentation charges per call while sampling charges per cycle.  Second,
share-of-time and ablation-cost are different questions: the inverse BWT is
35.81% of the optimized runtime yet its optimization was worth only 2%, because
a latency-bound pointer chase cannot be fixed by restructuring Python.

In hardware the same kernel maps naturally onto a dataflow design: the serial
canonical decode collapses into 20 parallel comparators and a priority encoder,
one symbol per cycle, verified both by a golden model across all 148,271
symbols and by RTL simulation under Icarus Verilog.  The variable-length nature
of the codes is precisely what rules out a systolic array here and makes this
the dataflow half of the two-paradigm story completed by the raytrace
accelerator.

The honest limit of the hardware proposal is the memory, not the logic: the
inverse BWT needs megabytes of on-chip SRAM to keep its promise, and without
that it degenerates to the same un-prefetchable DRAM pointer chase that makes
it slow in software.

================================================================================
7. CRITICAL REVIEW - KNOWN LIMITATIONS AND WHAT TESTING FOUND
================================================================================

This section exists because "it passed" is not the same as "it is correct".
Everything below was found by deliberately attacking the implementation after
it was written, and is stated rather than quietly fixed or hidden.

BUGS FOUND AND FIXED
--------------------
  fp32_add normalize (raytrace)  -  FOUND BY SIMULATION, FIXED
      Failed on its second test vector: 2+3 gave 6.5, 9-4 gave 2.5.  The
      carry-out path normalized the leading one to bit 26 while the
      leading-zero path normalized to bit 27, and the mantissa slice matched
      neither.  Fixed to one bit-26 convention, mant_raw = sum_n[25:3].

  Fake valid signalling (raytrace)  -  FOUND BY REVIEW, FIXED
      fp32_mul and fp32_add tied out_valid to 1 and discarded in_valid, so
      every downstream handshake was meaningless.  Valid now propagates one
      register per pipeline stage.

  Four array-level alignment bugs (raytrace)  -  FOUND BY REVIEW, FIXED
      ray_sphere_array computed t as v_arr[0] - sqrt(disc) for every candidate,
      carried no identity across the 25-cycle sqrt, advanced its index counter
      only on hits, and never re-initialized the running minimum between rays.
      None were visible from the PE testbench.  Fixed with an aligned delay
      line and a per-ray accumulator, and tb_ray_array.v now checks that the
      NEAREST of 8 spheres wins and is named correctly.

  Capture bank missing (raytrace)  -  FOUND BY REVIEW, FIXED
      All N PEs produce their results on the same cycle, but the serializer
      read them live over N cycles - sampling N different rays instead of the
      N spheres of one ray.  It only appeared to work because out_valid was
      stuck high.  Results are now latched into a capture bank and a ray_ready
      handshake tells the host the array accepts one ray every N cycles.

  L[] write address tied to zero (pyflate)  -  FOUND BY REVIEW, FIXED
      bzip2_accel_top wrote every decoded byte to L[0].  A write-address
      counter now advances with the MTF output stream.

KNOWN LIMITATIONS - STATED, NOT FIXED
-------------------------------------
  1. bzip2_accel_top is an integration sketch, not a complete decompressor.
     The T[] counting-sort engine that bwt_reverse_engine depends on is
     specified in the source but NOT implemented, so t_we is tied low.  The
     individual blocks (bit_window, huffman_decoder, mtf_unit,
     bwt_reverse_engine) are simulated and correct; the assembled top level
     elaborates but would not decompress a file.  What is missing is about
     n + 512 cycles of work: a 256-counter histogram, a prefix sum, and a
     second pass over L[] issuing one SRAM write per byte.

  2. build_decode_tables() does not skip zero-length symbols, while the
     baseline's HuffmanTable does (`if bits:`).  Instrumenting the real
     workload shows all 6 Huffman tables have minimum length 2, so no
     zero-length code ever occurs and the two agree.  It is a latent
     divergence on input this workload never produces, not an active bug.

  3. The optimized decoder was tested well beyond the benchmark file.  Fourteen
     additional bzip2 streams - empty, 1 byte, 1 KB of zeros, highly
     repetitive, 64 KB of random data, text, and a 900 KB multi-block file, at
     compression levels 1 and 9 - all round-trip correctly.  Randomised bzip2
     blocks remain unsupported, exactly as in the baseline.

  4. fp32_sqrt truncates, so the raytrace accelerator is NOT bit-identical to
     math.sqrt() - 1.16 ulp worst case over 6,008 samples.  The pyflate
     accelerator IS bit-exact.  A hardware-vs-software image comparison needs
     a tolerance; a pyflate one does not.

  5. Subnormal inputs and outputs are flushed to zero in the FP units.  This is
     a deliberate graphics-datapath choice, and it means a scene pushing into
     the subnormal range would diverge from the software reference.
