================================================================================
1. OVERVIEW
================================================================================

WHAT THE BENCHMARK DOES
-----------------------
raytrace is the toy ray tracer by Callum and Tony Garnock-Jones (2008).  It
renders a 100x100 image of a scene containing:

    1 large sphere        centre (1, 3, -10),  radius 2
    6 small spheres       centres (-3-0.4y, 2.3, -5), radius 0.4
    1 checkerboard plane  (Halfspace through the origin, normal +Y)
    2 point lights        (30, 30, 10) and (-10, 100, 30)

for a total of 8 intersectable objects.  Shading is Lambert diffuse plus a
specular reflection, recursing to depth 3.  Output is a PPM framebuffer.

Choosing this alongside pyflate was deliberate.  pyflate is integer, control-
flow and irregular-memory bound; raytrace is floating-point and allocation
bound.  They stress opposite parts of the machine and, as section 5 shows, they
motivate the two DIFFERENT accelerator paradigms from the lecture.

LIBRARIES USED
--------------
Only math (sqrt, tan, pi) and array (the framebuffer).  As with pyflate, the
point is to measure the interpreter doing real arithmetic, not a C library.

DATA STRUCTURES AND ALGORITHM
-----------------------------
  Vector / Point      three floats, distinguished only by behaviour.  Point -
                      Point yields a Vector; Point + Vector yields a Point.
                      The distinction is enforced at RUNTIME by isPoint() /
                      mustBeVector() calls inside every arithmetic operator.
  Sphere / Halfspace  geometry, each exposing intersectionTime() and normalAt()
  Ray                 origin Point + normalized direction Vector
  Scene               object list, light list, camera, recursion depth
  Canvas              array('B') RGB framebuffer

Per pixel: build a primary ray, test it against all 8 objects, take the nearest
hit, shade it (which casts shadow rays to each light and one reflection ray),
recurse.

                    +-- per pixel --------------------------+
                    |  Ray(eye, dir)   -> normalized()      |
                    |     |                                 |
                    |     v                                 |
                    |  8 x intersectionTime()               |
                    |     |                                 |
                    |     v  nearest hit                    |
                    |  colourAt()                           |
                    |     |-- reflection ray -> rayColour()  |  (depth <= 3)
                    |     +-- 2 lights x visibleLights()     |
                    |            +-- 8 x intersectionTime()  |
                    +---------------------------------------+

2. INITIAL ANALYSIS
================================================================================

METHODOLOGY
-----------
Same three-view approach as pyflate: perf record + flame graph for where,
cProfile for call counts, perf stat counters for why.  See report_pyflate.txt
section 2 for the two tooling traps (pyperf re-execs into a worker, and Python
function names need CPython 3.12's -X perf trampoline plus an intact
/tmp/perf-<pid>.map).  naranja7 runs 3.12.3, so the flame graphs here carry
py:: frames.

BASELINE PROFILE (perf, cycle-weighted, Python-level)
------------------------------------------------------
From results_naranja7/flamegraph_top.txt:

    Vector.dot                                    15.68%
    Sphere.intersectionTime                       11.76%
    Scene._lightIsVisible                          7.80%

    Vector.__init__                                4.72%

  Grouped: the tiny Vector/Point operations - __sub__, dot, scale, __init__,
  normalized - account for 47.45% of runtime.  Nearly half the program is spent
  in three-float arithmetic wrappers, not in the ray tracing algorithm.

CALL COUNTS (cProfile)
----------------------
  3,071,042 function calls for one 100x100 frame - 307 calls per pixel.
    509,871  Vector.dot
    277,865  Point.__sub__
    179,457  Sphere.intersectionTime

WHAT THE PROFILE ACTUALLY SAYS
------------------------------
  1. Sphere.intersectionTime is called 179,457 times for 10,000 pixels - about
     18 intersection tests per pixel, not 8.  The extra ones are shadow rays
     and reflection rays.  Intersection is THE kernel.

  2. Every one of the 509,871 Vector.dot calls begins with
     other.mustBeVector() - a method call whose only purpose is a type
     assertion.  Point.__sub__ similarly calls other.isPoint() 277,865 times.
     A large fraction of the "arithmetic" cost is dynamic type checking.  The
     perf grouping above makes this concrete: 47% of the runtime is in these
     wrappers.

  3. Scene._lightIsVisible contains a loop-invariant expression:

         for (o, s) in self.objects:
             t = o.intersectionTime(Ray(p, l - p))      # <-- inside the loop

     Ray(p, l - p) does not depend on o.  Its constructor calls normalized(),
     which calls magnitude(), which calls sqrt(dot(self)).  So the SAME shadow
     ray - including its square root - is reconstructed 8 times per light per
     shading point.  This is a plain bug, not a subtle trade-off, and it shows
     up as _lightIsVisible at 7.80% plus much of the scale/normalized time.

  4. Scene.rayColour allocates a list of 8 (object, t, surface) tuples for
     EVERY ray - primary, shadow and reflection alike - then scans it in
     firstIntersection().  ~180k tuples plus ~22k lists per frame, all
     immediately discarded.

  Additionally, no class defines __slots__, so every Vector, Point and Ray
  carries a per-instance __dict__ - and the renderer creates several per pixel.
  Vector.__init__ alone is 4.72%.

FLAME GRAPHS
------------
  results_naranja7/flamegraph_raytrace_baseline.svg   (130 distinct py:: frames)
  results_naranja7/flamegraph_raytrace_optimized.svg  ( 65 distinct py:: frames)

The baseline is a deep, narrow tower - the recursive rayColour -> colourAt ->
rayColour chain - resting on a very wide base of tiny Vector/Point operator
frames.  That "wide base of small frames" signature is the visual form of
finding 2: the leaves are type checks and operator dispatch, not floating-point
work.


================================================================================
3. OPTIMIZATIONS
================================================================================

CONSTRAINT: BIT-IDENTICAL OUTPUT
--------------------------------
The rendered image must be unchanged.  Floating-point addition is not
associative, so every expression below preserves the baseline's operand ORDER
and GROUPING exactly - the optimizations remove interpreter work, never
rearrange arithmetic.  tools/verify.py compares the full 30,000-byte RGB
framebuffer, and script_raytrace.sh additionally diffs the written PPM files.

O1 - HOIST THE SHADOW RAY OUT OF THE OBJECT LOOP
-------------------------------------------------
Construct Ray(p, l - p) once, before the loop over objects.  Identical result
(nothing in the loop mutates p or l), one sqrt instead of eight.

O2 - NO PER-RAY INTERSECTION LIST
----------------------------------
Track the running minimum inline instead of building a list of candidates and
scanning it.  The baseline's tie-breaking is preserved exactly: strict `<`
means the earliest object in the list wins a tie, so the same object is chosen.
Allocates nothing per ray.

O3 - REMOVE TYPE CHECKS FROM VECTOR ARITHMETIC
-----------------------------------------------
The hot paths know their operand types statically, so intersectionTime,
normalAt, normalized, reflectThrough and the Lambert loop operate directly on
raw floats: no dot(), no mustBeVector(), no temporary Vector objects.  The
public Vector/Point API keeps its semantics for any other caller.

O4 - __slots__ ON THE GEOMETRY CLASSES
---------------------------------------
Vector, Point, Ray, Sphere, Halfspace, Scene, Canvas and the surfaces all gain
__slots__: no per-instance __dict__, smaller objects, attribute access by fixed
offset instead of a dict lookup.

O5 - CHEAP ARITHMETIC AND ALLOCATION HOISTS
--------------------------------------------
Sphere caches radius*radius.  ycomp is computed once per scanline rather than
once per pixel (it depends only on y).  The Canvas blue channel is filled with
one slice assignment instead of a 30,000-iteration Python loop.

DELIBERATELY NOT DONE
---------------------
  * CheckerboardSurface.baseColourAt() calls v.scale(...) and DISCARDS the
    result, so checkSize never takes effect.  That is a real bug in the
    original, but fixing it would change the rendered image, and the brief
    requires identical output.  It is left exactly as-is and flagged here
    rather than silently preserved.
  * No numpy, no C extension: the benchmark measures the interpreter.
  * No BVH.  A bounding-volume hierarchy would beat all of the above for large
    scenes, but with 8 objects the traversal overhead exceeds the 8
    intersection tests it would save.  Worth stating explicitly, because it is
    the first thing a graphics person would propose - and here it is wrong.

READING THIS TABLE
------------------
As with pyflate, IPC is essentially flat (2.44 -> 2.52) while instructions
retired fell 2.57x against a 2.55x runtime improvement.  The speedup is
entirely "execute fewer instructions", not "execute them better".  Every
mustBeVector() call that disappeared was a real call: argument tuple, frame
push, return.

One row deserves attention because it looks like a regression:

    cache-miss RATE went UP, 1.20% -> 1.40%

while absolute misses fell 2.65x.  This is the same phenomenon the course's own
perf tutorial demonstrates with row-major versus column-major traversal: the
optimized code makes 3.08x fewer cache REFERENCES, because it is not allocating
and touching a swarm of short-lived Vector objects.  The references that remain
are the genuinely cold ones, so the ratio of misses to references rises even
though the machine stalls far less often.  A miss RATE in isolation is not a
performance metric; misses per unit of work is.

================================================================================
5. HARDWARE ACCELERATION PROPOSAL
================================================================================

TARGET AND DESIGN PATTERN
-------------------------
Target: ray-sphere intersection - 36.02% of the optimized runtime and the
kernel the ablation ranks first (+51%).

Unlike pyflate's Huffman decoder, this kernel has FIXED operand count, FIXED
latency and NO data-dependent control flow.  Every test computes exactly:

    c    = centre - ray.point                 3 subtractions
    v    = c . ray.vector                     3 mul + 2 add
    cc   = c . c                              3 mul + 2 add
    disc = r^2 - (cc - v*v)                   1 mul + 2 sub
    t    = v - sqrt(disc)                     1 sqrt + 1 sub

That regularity is what a SYSTOLIC ARRAY wants, and it is why this design
differs fundamentally from the pyflate accelerator:

    pyflate   variable-length codes -> data-dependent rate -> DATAFLOW
    raytrace  fixed-shape FP kernel  -> fixed cadence       -> SYSTOLIC ARRAY

Sphere parameters are WEIGHT-STATIONARY: (cx, cy, cz, r^2) are preloaded into
the PEs once per frame and stay there while rays stream through - structurally
the same trick as the TPU preloading weights and streaming activations.

INTERFACES: INPUTS AND OUTPUTS
------------------------------
  Clock / reset       clk, rst_n.  Target 1 GHz in a 16 nm-class process.
                      Critical path is inside fp32_add's normalize shifter
                      (leading-zero count on a cancelling subtraction), which
                      is why the datapath is a MAC chain rather than a wide
                      adder tree.

  Weight load         w_load, w_idx[7:0], w_cx/w_cy/w_cz/w_r2 [31:0]
                      One sphere per cycle; 8 cycles to load this scene.

  Ray stream          px,py,pz,vx,vy,vz [31:0], ray_valid
                      192 bits/ray.  At 1 GHz and one ray per 8 cycles that is
                      24 GB/s - fine on-die, but a strong argument for
                      generating rays ON the accelerator rather than streaming
                      them across PCIe.

  Result              t_nearest[31:0], obj_nearest[7:0], hit_any, result_valid

  Numeric format      IEEE-754 binary32.  Round-to-nearest-even on mul/add;
                      subnormals flushed to zero (standard for a graphics
                      datapath - it removes the subnormal shifter from the
                      critical path for values that cannot move an 8-bit
                      colour channel).

  Latencies           fp32_mul  2 cycles, throughput 1/cycle
                      fp32_add  2 cycles, throughput 1/cycle
                      fp32_sqrt 24 cycles, throughput 1/cycle
                      PE end-to-end ~14 cycles, fully pipelined

INTERNAL ARCHITECTURE
---------------------
Each ray_sphere_pe holds one sphere and computes (v, disc, hit) for the ray
passing it, using 3 fp32_add for the centre subtraction, 6 fp32_mul and 4
fp32_add for the two dot products, then 1 mul and 2 adds for the discriminant.

The square root is NOT replicated per PE.  fp32_sqrt is 24 pipeline stages -
by far the largest block - and one fully pipelined instance retires one
candidate per cycle.  With N_SPHERES = 8 the sqrt therefore sets throughput at
one ray per 8 cycles.  This is the central area/performance decision, quantified
below.

fp32_sqrt uses the classic restoring bit-by-bit integer square root on the
significand, unrolled into 24 stages.  Radicand scaling:
    E even -> radicand = {1,m} << 23, root = sqrt(1.m)   * 2^23, exp = E/2
    E odd  -> radicand = {1,m} << 24, root = sqrt(2*1.m) * 2^23, exp = (E-1)/2
Either way the root lands in [2^23, 2^24), already normalized, so no
post-normalize shifter is needed.

VERIFICATION - ACTUALLY RUN, AND IT FOUND A REAL BUG
-----------------------------------------------------
  1. sqrt golden model (hw/raytrace_mac/sqrt_model.py), 6,008 samples:

         24 stages, truncating (as built)   worst 1.16 ulp
         25 stages + round-to-nearest       worst 0.69 ulp
         sqrt(1), sqrt(4), sqrt(9), sqrt(16), sqrt(0.25)  all bit-exact

     The as-built unit truncates, so it is NOT bit-identical to math.sqrt().
     That is a deliberate trade (it removes a 24-bit incrementer from the tail)
     and it is why a hardware-vs-software image comparison here needs a
     tolerance, in contrast to the pyflate accelerator, which is bit-exact.

  2. RTL simulation, Icarus Verilog 12.0 on naranja7
     (results_naranja7/rtl_simulation.txt):

         ok  fp32_mul 2*3 = 40c00000
         ok  fp32_add 2+3 = 40a00000
         ok  fp32_add 9-4 = 40a00000
         ok  fp32_sqrt(4) = 40000000
         ok  fp32_sqrt(9) = 40400000
         ok  pe v    = 41200000   (10.0)
         ok  pe disc = 40800000   ( 4.0)
         ok  pe hit  = 1
         TB PASS: all checks bit-exact

     The worked case, also computable by hand:
         sphere centre (0,0,-10), r=2 -> r^2 = 4
         ray    origin (0,0,  0), dir (0,0,-1)
         c = (0,0,-10);  v = 10;  cc = 100
         disc = 4 - (100 - 100) = 4
         t    = 10 - sqrt(4) = 8
     Every intermediate is exactly representable in binary32, so it must be
     bit-exact end to end - no tolerance needed.

  3. Randomized verification (hw/raytrace_mac/gen_fp_vectors.py):

         TB PASS: 400 random vectors, add and mul both bit-exact

     400 operand pairs checked against binary32 arithmetic computed in Python
     with struct.  A quarter of them are deliberately near-cancelling
     subtractions, because that is the case which exercises the adder's long
     left-shift normalize path.

  THE BUG.  The FIRST run of tb_ray_sphere failed: 2+3 produced 6.5 and 9-4
  produced 2.5.  fp32_add had two coupled off-by-one errors - the carry path
  normalized the leading one to bit 26 while the leading-zero path normalized
  it to bit 27, and the mantissa slice sum_n[26:4] matched neither convention.
  Fixed to a single bit-26 convention with mant_raw = sum_n[25:3].  The PE
  failures were downstream consequences and cleared with the same fix.

  This is the honest value of simulating rather than asserting: the module had
  been written carefully, reviewed, and was completely wrong on its second test
  vector.  The randomized testbench was added afterwards precisely because
  three hand-picked cases are not enough to trust a floating-point unit.

ACCELERATION JUSTIFICATION AND EXPECTED SPEEDUP
-----------------------------------------------
Why this component: 36.02% of the optimized runtime, 179,457 calls per frame of
identical shape, and embarrassingly parallel across objects.

Estimate, with assumptions stated:

    Intersection tests per frame            179,457
    Array: 1 ray (8 spheres) / 8 cycles     ~22,432 ray-groups
    At 1 GHz                                ~22 us of array time

    Optimized software (naranja7)           217 ms
    Baseline software (naranja7)            554 ms

Assumptions: rays are generated on-chip or streamed at full rate, shading and
the recursive control flow still run on the host, and transfer overhead is
excluded.  The honest caveat is Amdahl: intersection is 36.02% of the optimized
runtime, so even an infinitely fast intersection unit caps the whole-frame
speedup at 1/(1-0.3602) = 1.56x.  Quoting the ~10,000x kernel ratio without
that caveat would be meaningless.  Accelerating the shading path as well is
what would be needed for a real product - which is the path GPUs actually took.

HW/SW INTERFACE
---------------
  Rule 1 - users do not change their code.  A renderer still calls
      scene.render(); the accelerator sits under the intersection primitive.
  Rule 2 - changes confined to the library.  The geometry layer gains a
      batched intersect(rays, spheres) entry point; the scene uploads once per
      frame.
  Rule 3 - never break the user's code.  The array handles spheres only.
      Halfspaces, and any scene with more objects than PEs, fall back to the
      CPU path - which is why the software keeps a working scalar
      implementation.

  Batching is essential, not incidental: one ray per transaction would be
  dominated by descriptor overhead.  The driver accumulates a tile of rays and
  issues them as one DMA, the same reason GPUs shade in warps.

PERFORMANCE / AREA / POWER TRADE-OFFS
-------------------------------------
  The sqrt/area knob, quantified:

    shared sqrt (as built)   1 sqrt unit    1 ray / 8 cycles   smallest area
    one sqrt per PE          8 sqrt units   1 ray / 1 cycle    ~8x sqrt area

  fp32_sqrt at 24 stages x ~50 bits of pipeline registers is roughly comparable
  in area to the entire arithmetic datapath of one PE, so replicating it
  approximately doubles total array area for an 8x throughput gain.  For a
  throughput-limited renderer that is a good trade; for an area-limited edge
  part it is not.  The design is parameterized so both points are buildable.

  Accuracy vs area, also quantified (sqrt_model.py): the 25th stage plus a
  24-bit rounding incrementer buys 1.16 ulp -> 0.69 ulp.  For shading that
  precision is not needed, so the cheaper unit ships.

  Scaling N_SPHERES: area grows linearly, but so does the serializer depth
  feeding the shared sqrt, so throughput per ray stays at N cycles.  Beyond
  ~16 spheres a second sqrt unit is a better spend than more PEs.

  Precision: dropping to bfloat16 for the dot products would roughly halve
  multiplier area and power.  It is rejected - 8 mantissa bits is not enough
  for a discriminant that is the difference of two large, nearly equal numbers
  (cc - v*v), which is exactly where catastrophic cancellation lives.  This is
  the one place in the design where precision is not negotiable.  Note that the
  fp32_add bug above lived in precisely this cancellation path, which is a
  useful reminder of how delicate it is.

  Power: the multipliers dominate dynamic power.  Clock-gating a PE whose
  sphere is behind the ray origin (v < 0, known early) skips most of the
  datapath for a large share of tests in a typical scene.


================================================================================
6. CONCLUSION
================================================================================

The optimized renderer is 2.55x faster than the baseline on naranja7 and
produces a bit-identical image, verified over the full 30,000-byte framebuffer.

The most valuable finding was not clever: Scene._lightIsVisible rebuilt the same
shadow ray - square root included - once per object, and hoisting that one
loop-invariant expression is worth 49% on its own.  The second was that the
tiny Vector/Point wrappers, and the 509,871 mustBeVector() type assertions
inside them, accounted for 47% of runtime - more than the arithmetic they were
guarding.  Both came from the profile; neither is visible from reading the code
at normal speed.  The counterpoint is equally instructive: eliminating ~200,000
allocations per frame, the thing one instinctively reaches for, was worth only
7%.

The hardware counters confirm the mechanism rather than merely the result: IPC
moved 2.44 -> 2.52, essentially flat, while instructions retired fell 2.57x
against a 2.55x speedup.  And the cache-miss RATE rising from 1.20% to 1.40%
while absolute misses fell 2.65x is the same trap the course's own perf
tutorial sets with row- versus column-major traversal - a rate is not a
performance metric.

In hardware this kernel is the systolic counterpart to pyflate's dataflow
decoder.  Fixed operand count, fixed latency and no data-dependent control make
a weight-stationary array of intersection PEs the natural structure, with
sphere parameters preloaded and rays streamed through exactly as the TPU
preloads weights.  The interesting engineering decision is not the multipliers
but the square root: sharing one 24-stage pipeline across 8 PEs costs 8x
throughput and saves roughly half the array area.

Simulating the RTL rather than merely writing it was worth doing: fp32_add was
wrong on its second test vector, in the cancellation path that the precision
analysis above identifies as the most delicate part of the whole datapath.

The honest limit is Amdahl's law.  Intersection is 36% of the optimized
runtime, so accelerating it perfectly caps the frame speedup at 1.56x.  A
useful product would have to move shading onto the accelerator as well.

================================================================================
7. CRITICAL REVIEW - KNOWN LIMITATIONS AND WHAT TESTING FOUND
================================================================================

This section exists because "it passed" is not the same as "it is correct".
Everything below was found by deliberately attacking the implementation after
it was written, and is stated rather than quietly fixed or hidden.

BUGS FOUND AND FIXED
--------------------
  fp32_add normalize (raytrace)  -  FOUND BY SIMULATION, FIXED
      Failed on its second test vector: 2+3 gave 6.5, 9-4 gave 2.5.  The
      carry-out path normalized the leading one to bit 26 while the
      leading-zero path normalized to bit 27, and the mantissa slice matched
      neither.  Fixed to one bit-26 convention, mant_raw = sum_n[25:3].

  Fake valid signalling (raytrace)  -  FOUND BY REVIEW, FIXED
      fp32_mul and fp32_add tied out_valid to 1 and discarded in_valid, so
      every downstream handshake was meaningless.  Valid now propagates one
      register per pipeline stage.

  Four array-level alignment bugs (raytrace)  -  FOUND BY REVIEW, FIXED
      ray_sphere_array computed t as v_arr[0] - sqrt(disc) for every candidate,
      carried no identity across the 25-cycle sqrt, advanced its index counter
      only on hits, and never re-initialized the running minimum between rays.
      None were visible from the PE testbench.  Fixed with an aligned delay
      line and a per-ray accumulator, and tb_ray_array.v now checks that the
      NEAREST of 8 spheres wins and is named correctly.

  Capture bank missing (raytrace)  -  FOUND BY REVIEW, FIXED
      All N PEs produce their results on the same cycle, but the serializer
      read them live over N cycles - sampling N different rays instead of the
      N spheres of one ray.  It only appeared to work because out_valid was
      stuck high.  Results are now latched into a capture bank and a ray_ready
      handshake tells the host the array accepts one ray every N cycles.

  L[] write address tied to zero (pyflate)  -  FOUND BY REVIEW, FIXED
      bzip2_accel_top wrote every decoded byte to L[0].  A write-address
      counter now advances with the MTF output stream.

KNOWN LIMITATIONS - STATED, NOT FIXED
-------------------------------------
  1. bzip2_accel_top is an integration sketch, not a complete decompressor.
     The T[] counting-sort engine that bwt_reverse_engine depends on is
     specified in the source but NOT implemented, so t_we is tied low.  The
     individual blocks (bit_window, huffman_decoder, mtf_unit,
     bwt_reverse_engine) are simulated and correct; the assembled top level
     elaborates but would not decompress a file.  What is missing is about
     n + 512 cycles of work: a 256-counter histogram, a prefix sum, and a
     second pass over L[] issuing one SRAM write per byte.

  2. build_decode_tables() does not skip zero-length symbols, while the
     baseline's HuffmanTable does (`if bits:`).  Instrumenting the real
     workload shows all 6 Huffman tables have minimum length 2, so no
     zero-length code ever occurs and the two agree.  It is a latent
     divergence on input this workload never produces, not an active bug.

  3. The optimized decoder was tested well beyond the benchmark file.  Fourteen
     additional bzip2 streams - empty, 1 byte, 1 KB of zeros, highly
     repetitive, 64 KB of random data, text, and a 900 KB multi-block file, at
     compression levels 1 and 9 - all round-trip correctly.  Randomised bzip2
     blocks remain unsupported, exactly as in the baseline.

  4. fp32_sqrt truncates, so the raytrace accelerator is NOT bit-identical to
     math.sqrt() - 1.16 ulp worst case over 6,008 samples.  The pyflate
     accelerator IS bit-exact.  A hardware-vs-software image comparison needs
     a tolerance; a pyflate one does not.

  5. Subnormal inputs and outputs are flushed to zero in the FP units.  This is
     a deliberate graphics-datapath choice, and it means a scene pushing into
     the subnormal range would diverge from the software reference.
