HOW TO REPRODUCE
================================================================================

  Everything runs inside the course QEMU image.  From /scratch/$USER on the
  assigned naranja host:

    qemu-img create -f qcow2 -b jammy-server-cloudimg-amd64-disk-kvm.img \
                    -F qcow2 work.qcow2
    qemu-system-x86_64 -m 4096 -smp 8 -cpu host,pmu=on -accel kvm \
        -nographic -nic user,model=virtio-net-pci \
        -drive file=work.qcow2,format=qcow2
    # login root / ubuntu, copy this directory in, then:

    ./script_pyflate.sh all
    ./script_raytrace.sh all
    ./tools/regress.sh          # ten correctness + RTL checks

  work.qcow2 is an OVERLAY, so the course image is never written to.

  pmu=on is not optional: without it the guest has no virtual PMU and perf
  answers <not supported> for every hardware event.  With it, the counter
  tables in both reports are reproducible.


A NOTE ON TOOLING, BECAUSE IT SHAPED THE METHOD
================================================================================

  Four things about perf inside this guest were established by testing, not
  assumed.  Each is documented in report_pyflate.txt section 2, and
  ./script_*.sh setup re-checks all of them and prints the answers.

    1. Hardware COUNTING works - but only because of -cpu host,pmu=on.
    2. Hardware SAMPLING does not work: perf record on a hardware event
       captures zero samples even though perf stat counts the same event.
       Flame graphs therefore use -e cpu-clock.
    3. Six events in one perf stat run make one read exactly 0.  That is
       counter multiplexing, not an unsupported event.  All counter figures
       were taken in groups of two.
    4. CPython 3.10 predates the -X perf trampoline, so perf cannot name
       Python functions here.  py-spy provides the Python-level attribution.
